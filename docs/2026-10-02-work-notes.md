### 1.4 不具合修正 (ビルド 29)

- **長い返答のあとに返信しようとしてアプリが固まった**: アプリは CPU 100% で回り続けていた。iOS が残した CPU 使用過多のレポート (`cpu_resource`) では、メインスレッドがすべて SwiftUI / AttributeGraph のレイアウト計算の中にあり、推論側ではなかった。最初の返答が出力上限の 512 トークンまで伸び、その長い返答を表示したままキーボードを開いたときに、画面のレイアウトが無限ループしたと判断した。
  - 対策: 会話一覧を遅延表示の部品 (LazyVStack) から通常の VStack に変更、トークンごとの自動スクロールをやめて 1 行分程度ごとに変更、モデル選択欄と入力欄を safe area に置いてキーボードに追従させる、長文のテキスト選択をやめて長押しの「コピー」に変更。
  - レポートには記号情報がないため、どの部品がループしたかまでは特定できていない。**直ったかは未確認** (実際に入力して確かめる必要がある)。
- **チャット画面でキーボードを閉じられなかった**: 別 PC で HF 検索などに入れた「完了」ボタンの仕組み (`keyboardDismissible()`) がチャット画面だけ付いていなかった。「完了」、会話の下スクロール、会話部分のタップで閉じられるようにした。
- **画像・音声アイコンのタップ判定が狭かった**: 画像・音声・送信・停止ボタンを 44 ポイント四方 (iOS の推奨サイズ) に広げた。
- 補足: 固まる直前、アプリの起動直後に iOS のメモリ警告でモデルが一度アンロードされていた。今回の固まりとは別件として記録しておく。

## 2. 検討: KV キャッシュの再利用

### 2.1 現状

再利用は一切していない。毎回、会話全体を最初から計算し直している。

- llama.cpp (GGUF): リクエストのたびに最初に KV キャッシュを全消去し (`llama_memory_clear`)、システム指示・過去のすべてのターン・すべての画像と音声を、新しい入力と一緒に計算し直している。画像・音声のエンコードも毎回やり直している。
- LiteRT-LM: リクエストのたびに会話オブジェクトを作り直し、過去のメッセージを最初から流し込み直している。
- 影響 (別 PC での計測、コンテキスト 4096): 1 ターンの時間は会話の最初が 1.6 秒、3900 トークン付近で 29 秒。画像を毎回付けると最後は 40 秒。入力の評価が約 200 トークン/秒なので、履歴が長いほど待ち時間がそのまま伸びる。チャットタブも同じ仕組みなので、会話が長くなると同様に遅くなる。

### 2.2 再利用の範囲

「入力に関する部分のみ」ではなく、モデル自身の過去の返答も含めた会話全体が対象になる。

- サーバーは会話を覚えておらず (ステートレス)、クライアント (PC のプログラムやチャット画面) が毎回「システム指示 + 過去の全ターン (ユーザー入力とモデルの返答) + 新しい入力」をまとめて送ってくる。モデルにとっては、この送られてきた列がそのままコンテキスト。
- 再利用は、この列の計算結果 (KV キャッシュ) のうち、前回と先頭から一致する部分を計算し直さない、というだけの最適化。新しい記憶を持たせるわけではない。何がコンテキストに入るかは、これまでどおりクライアントが送る内容で決まる。
- 前回の返答は生成したときにキャッシュに入っているので、次のターンではそれも再利用できる。ただし、返答を文字列に戻して送り直すとトークン分割が変わることがあり、その場合はその地点から後ろだけ計算し直しになる。
- 画像・音声は内容のハッシュで同一判定できる (mtmd のビットマップには FNV ハッシュの ID が付く) ので、過去の画像・音声を再エンコードせずに済む。

### 2.3 方針案 (未着手、未承認)

前回の入力列 (テキストのトークンと、画像・音声のチャンク) をメモリに残し、新しいリクエストと先頭が一致する位置までは KV キャッシュをそのまま使い、一致しなくなった位置から後ろだけを消して (`llama_memory_seq_rm`) 計算し直す。会話を続けるだけなら、毎ターンの計算は新しく追加された分だけになる。

## 3. 調査: コンテキスト圧縮 (結論は未定)

### 3.1 コーディングエージェントのハーネスでの方式

大きく 3 つの方式がある。

**A. 要約で置き換える (compaction / summarization)**

| ハーネス | いつ動くか | 何を残すか |
| --- | --- | --- |
| Claude Code | コンテキストの約 95% で自動。`/compact` で手動 (重点を指示できる) | 会話全体を LLM で要約して置き換える。要約では「やったこと・進行中の作業・関係ファイル・次の手順・ユーザーの指示や制約」を残すよう指示する。永続させたいルールは要約に頼らず CLAUDE.md に書く設計 |
| Codex CLI | トークン上限の設定値 (`model_auto_compact_token_limit`、モデルにより 180k〜244k)。`/compact` | 要約に加えて、直近のユーザー発言約 2 万トークンと最初のコンテキストを原文のまま残す |
| OpenCode | 「コンテキスト上限 − 出力上限」を超えたとき | 要約とは別に、古いツール出力を間引く。直近 4 万トークン分のツール出力は保護 |
| Gemini CLI | 既定で 70% (当初の 95% から引き下げ。設定で変更可) | 古いターンを要約し、直近のやり取りを残す |
| Aider | 履歴が上限 (`max-chat-history-tokens`) を超えたとき | 安いモデル (weak model) で古い履歴を要約 |
| Amp | 自動圧縮なし | 必要な情報を新しいスレッドへ引き継ぐ「Handoff」と、会話を短く保つ運用 |

**B. 古い観測結果だけ消す (observation masking / context editing)**

- 古いツール出力をプレースホルダーに置き換え、行動 (何をしたか) の記録は残す。LLM 呼び出しが不要。
- Anthropic API の context editing (`clear_tool_uses`) は、閾値 (既定 10 万トークン) を超えると古いツール結果から順にサーバー側で消し、直近の数件 (既定 3) は残す。
- OpenHands にも同等のコンデンサ (ObservationMaskingCondenser) と、要約型のコンデンサ (最初の N 件と最後の M 件を残し、間を要約) がある。

**C. 外部メモリ**

- 消してはいけない事実を、会話の外 (ファイルや memory tool) に書き出しておき、必要なときに読み直す。Anthropic API では memory tool を context editing の対象外にできる。

**研究結果**: JetBrains の論文 "The Complexity Trap" (NeurIPS 2025 DL4Code ワークショップ) では、SWE-bench Verified で、古い観測結果を一定ターン数より前から置き換えるだけの単純な方式 (observation masking) が、LLM 要約と同等の正答率をより低いコストで出した (例: Qwen3-Coder 480B で、何もしない場合 53.8% → masking 54.8%)。

**記憶の欠落について**: 各ハーネスでも報告がある。

- 要約を繰り返すと精度が落ちる (Codex CLI、Claude Code)
- 作業の途中で圧縮されると脱線することがある (Claude Code)

このため「重要な指示は要約に頼らず別に固定する」「直近は原文で残す」が共通の対策になっている。

### 3.2 このアプリに当てはめた場合の検討

- **実装する場所**: API 経由の会話は、PC 側のクライアントが履歴を管理して毎回送ってくるので、圧縮もクライアント側の責任になる (サーバーが勝手に履歴を削ると、送られた内容と違うものを推論することになる)。アプリで圧縮を実装するとすれば、アプリ自身がクライアントであるチャットタブ。
- **KV キャッシュ再利用との相性**: 圧縮すると会話の先頭が変わるので、再利用の効果がその時点でいったん消える (圧縮後の 1 ターンは全体を計算し直す)。毎ターン少しずつ削る方式 (スライディングウィンドウ) は再利用と相性が悪い。ハーネスと同じく「閾値で、まとめて、たまに」圧縮するのが合う。
- **一番コンテキストを食うのは画像と音声**: 画像は 1 枚 52〜270 トークン (320×240 以下で 52、640×480 で 134、1280×960 以上で 270)、音声は 1 秒 25 トークン (30 秒で 750)。古いターンの画像・音声を「[画像: 前のターンで説明済み]」のような短い置き換えにするのは、B の方式そのもので、LLM 呼び出しも要らない。ただし、後から「最初の写真の左にあった物は?」のように聞かれると答えられなくなる。
- **要約の制約**: 要約は同じモデル (E2B) で行うことになり、数秒〜十数秒かかる (その間は推論できない)。小さいモデルなので要約の質にも限界がある。別 PC での計測では、E2B は 54 ターンの会話で過去の内容を満杯まで正しく答えられていたので、コンテキストに入っている限りは記憶できている。要約で欠落するリスクの方が大きい可能性がある。
- **要約を行う場合の欠落対策の候補**:
  - システム指示と最初の依頼は原文で固定
  - 直近の数ターンは原文
  - 要約の項目を決めておく (決まった事実・ユーザーの条件・未解決の質問)
  - 画面上の会話履歴は消さずに全文を残す (表示と、モデルに送る内容を分ける)
- **コンテキストサイズ自体を上げる選択肢**: 別 PC の計測では、設定の選択肢 1024〜8192 はモデル (最大 131,072) やメモリの制約ではなかった。KV キャッシュは 1 トークン 18 KiB なので、16k で約 290 MiB、32k で約 580 MiB。ただし、2.2 の再利用がない状態では、コンテキストが大きいほど 1 ターンの待ち時間も伸びる。

### 3.3 未決定の点

- 圧縮を実装するかどうか、実装するならどの方式か (画像・音声の置き換えだけにするか、要約まで行うか)。
- 閾値 (例: 70%) と、何ターン分を原文で残すか。
- 置き換えや要約をしたことを、利用者にどう見せるか (知らないうちに忘れられるのを避ける)。
- API クライアント向けに何か提供するか (例: 推奨する圧縮方法の文書化のみ、またはオプトインのサーバー側機能)。

暫定的な提案順は ① KV キャッシュの先頭一致の再利用 → ② コンテキスト 16k / 32k の選択肢 → ③ 古い画像・音声の置き換え → ④ 閾値での要約。③④ は ①② の効果を測ってから判断する。

## 4. 音声入力の上限 30 秒の根拠

- Google の Gemma 4 公式ドキュメントに「Audio supports a maximum length of 30 seconds」とあり、モデルの仕様上の上限。アプリの録音上限もこれに合わせた。
- 同じドキュメントで「音声 1 秒 = 25 トークン」(16 kHz) とされ、30 秒で 750 トークンになる。実測 (13 秒で約 330 トークン、テキスト分を含む) とも一致した。
- llama.cpp は長い音声を 30 秒ごとに区切って処理するので技術的には送れるが、モデルが想定しているのは 30 秒まで。長い音声は 30 秒ずつ分けて複数添付するのが安全。
